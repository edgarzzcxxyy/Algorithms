# Behavioral Question Notes

## General
- Show behavior: take the initiative (set up the meeting yourself), break work into smaller pieces, describe concrete actions.
- Use STAR and always state the result (recognition, bonus, what shipped) in Result / Reflection.
- Stories can be reused across questions. The challenge story's execution steps (break down → milestones → design review) also answer "meet a deadline" and "handle pressure".
- Most frequently asked: challenge, conflict, difficult people. Prepare one story for each question in the list below.

## Most challenging project
- Story options: school multi-thread project (first time with multithreading), or the internship project (first time with that tech stack).
- What the feature was and how you broke it down.
- How you learned the different tech stack.
- Actions: allocate time, smaller design pieces, milestones, design review.

## Conflict (non-technical)
- Avoid a pure tech-choice conflict (e.g. NoSQL vs MySQL).
- Possible sources:
  - Short-term vs long-term solution under a time requirement
  - Customer / product requirements
  - Different guesses that only an experiment can settle (run the job and see)
- Actions: analyze the trade-off and deliver in phases; set up a meeting with a few slides showing the trade-off; come with an answer and your reasoning.
- Story: end-of-internship demo. Mentor suggested recording a video; I pushed for a live demo of the data migration because I had rehearsed it several times and it finished within the time slot. Recorded a video as a backup. Result: the live demo succeeded; named an exceptional intern and received a bonus (say "bonus", no amount). Explain clearly why you insisted.

## Difficult people (tell one of these, not both)
- Teammate not doing their part
  - Don't do it for them (doesn't scale).
  - Set up a meeting, find what's blocking them, provide resources; re-plan tasks if time is the problem; regular check-in meetings.
- Teammate changing your work without telling you
  - Set up a meeting and agree on how to collaborate; ask for changes to be discussed or done together.
  - Avoid "we worked at different times so we wouldn't overlap": it can sound like the work wasn't divided up front.
  - Better framing: work was split (e.g. frontend / backend), but the backend changed the API format without telling the frontend.
